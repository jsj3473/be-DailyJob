# 이번 주 학습 회고

## 1. Java 기본 문법과 메모리 구조 학습

이번 주에는 Java의 문자열, 컬렉션, 제네릭, JVM 실행 구조를 중심으로 학습하였다.

먼저 `String`의 불변성에 대해 정리하였다. 문자열 리터럴로 생성한 문자열은 문자열 상수 풀에 저장되며, 같은 값의 문자열은 동일한 주소를 참조할 수 있다. 반면 `new String()`을 사용하면 힙 메모리에 새로운 문자열 객체가 생성된다. `String` 객체는 불변 객체이기 때문에 문자열을 덧붙이더라도 기존 객체의 내부 데이터가 변경되는 것이 아니라 새로운 문자열 객체가 생성되고 참조 주소가 바뀐다. 따라서 문자열을 반복적으로 더하면 객체 생성과 메모리 해제가 계속 발생할 수 있다.

이를 해결하기 위한 방식으로 `StringBuilder`와 `StringBuffer`를 학습하였다. 두 클래스는 문자열을 가변적으로 다룰 수 있어 기존 데이터에 새로운 문자열을 이어 붙이는 방식으로 동작한다. `StringBuilder`는 동기화를 보장하지 않기 때문에 단일 스레드 환경에서 빠르게 사용할 수 있고, `StringBuffer`는 락을 사용하여 스레드 안전성을 제공하지만 그만큼 성능 비용이 발생할 수 있다는 점을 이해하였다.

자료구조 측면에서는 배열과 리스트의 차이를 정리하였다. 배열은 크기가 고정되어 있고 메모리에 연속적으로 저장되므로 인덱스를 통한 접근이 빠르다. 반면 리스트는 크기가 동적으로 증가할 수 있으며, 내부적으로 필요한 경우 더 큰 공간을 한 번에 확보하여 데이터를 관리한다. 또한 `LinkedList`는 삽입과 삭제에 유리하다고 배우지만, 실제로는 조회 성능이 떨어지고 메모리 접근 효율이 낮기 때문에 일반적인 상황에서는 `ArrayList`가 더 자주 사용된다는 점을 학습하였다.

제네릭에 대해서는 타입 안정성과 캐스팅 제거라는 관점에서 이해하였다. 제네릭을 사용하지 않으면 하나의 자료구조에 다양한 타입의 객체를 넣을 수 있지만, 꺼낼 때마다 명시적인 형변환이 필요하고 런타임 오류 가능성이 커진다. 반면 제네릭을 사용하면 자료구조가 관리할 타입을 컴파일 시점에 제한할 수 있어 캐스팅이 불필요하고 타입 안정성을 높일 수 있다.

## 2. 데이터베이스 모델링 학습

데이터베이스 수업에서는 데이터 모델링의 개념과 ERD 설계 방식을 학습하였다. 데이터 모델링은 현실 업무 요구사항에 맞춰 엔터티, 관계, 도메인 등을 정의하고 이를 데이터베이스 스키마로 설계하는 과정이라고 이해하였다.

모델링은 크게 개념 설계, 논리 설계, 물리 설계 단계로 나뉜다. 개념 설계는 업무에 필요한 핵심 개념을 추상적으로 정리하는 단계이고, 논리 설계는 엔터티와 관계를 구체적으로 분리하고 정규화된 구조를 만드는 단계이다. 물리 설계는 논리 모델을 실제 DBMS에 맞는 테이블, 컬럼, 제약조건, 인덱스 등의 스키마로 변환하는 단계이다.

엔터티의 종류도 정리하였다. 개체 엔터티는 회원, 상품처럼 명사로 표현되는 주요 대상을 의미하고, 행위 엔터티는 주문, 결제처럼 어떤 행위나 사건의 기록을 의미한다. 또한 슈퍼타입과 서브타입은 모델링 단계에서 공통 속성과 개별 속성을 분리하기 위한 개념이며, 실제 구현에서는 하나의 테이블에 합칠 수도 있고 여러 테이블로 분리할 수도 있다는 점을 이해하였다.

관계 측면에서는 식별 관계와 비식별 관계를 학습하였다. 부모로부터 전달받은 외래키가 자식 테이블의 기본키 일부가 되면 식별 관계이고, 단순한 일반 속성으로 존재하면 비식별 관계이다. ERD의 까마귀발 표기법에서는 이를 실선과 점선으로 구분한다. 또한 M:N 관계는 직접 구현할 수 없기 때문에 교차 엔터티로 분해해야 한다. 예를 들어 하나의 주문은 여러 상품을 가질 수 있고, 하나의 상품도 여러 주문에 포함될 수 있으므로 `주문상품`이라는 교차 엔터티를 만들어 1:N, N:1 관계로 풀어야 한다.

## 3. Java 실행 과정과 JVM 구조 학습

IntelliJ에서 Java 프로그램을 실행했을 때 내부적으로 어떤 과정이 일어나는지도 정리하였다. 실행 버튼을 누르면 먼저 Gradle이 빌드 작업을 수행한다. Gradle은 프로젝트에 필요한 라이브러리와 의존성을 확인하고, 필요한 경우 자동으로 다운로드한다. 이후 내부적으로 `javac` 컴파일러를 실행하여 `.java` 파일을 `.class` 바이트코드 파일로 변환한다. 이 과정이 컴파일 타임이다.

컴파일이 완료되면 IntelliJ는 `java Main`을 실행하고, 운영체제는 `java.exe`, 즉 JVM을 하나의 프로세스로 생성한다. JVM 프로세스에는 가상 주소 공간이 할당되고, Class Loader가 필요한 `.class` 파일과 Java 표준 라이브러리 클래스를 읽어온다. 운영체제는 디스크의 파일을 JVM 프로세스 메모리로 적재하고, Class Loader는 이를 Method Area에 저장한다.

JVM 메모리 구조도 함께 학습하였다. Method Area에는 클래스 메타데이터, 메서드 바이트코드, 런타임 상수 풀, static 변수 등이 저장된다. Heap Area에는 `new`로 생성된 객체와 배열이 저장되며, 모든 스레드가 공유하고 GC가 관리한다. Java Stack은 스레드마다 하나씩 생성되며, 메서드 호출 시 Stack Frame이 만들어지고 지역변수 등이 저장된다. PC Register는 각 스레드마다 존재하며 현재 실행 중인 바이트코드 명령어의 위치를 가리킨다. Native Method Stack은 JNI를 통해 C/C++ 등의 네이티브 메서드를 호출할 때 사용된다.

실행 과정에서는 Execution Engine이 바이트코드를 실행한다. 초기에는 Interpreter가 바이트코드를 한 줄씩 해석하여 실행하지만, 특정 메서드가 자주 호출되면 JVM은 이를 Hot Method로 판단한다. 이후 JIT Compiler가 해당 바이트코드를 현재 CPU 아키텍처에 맞는 기계어로 컴파일하고, 이를 코드 캐시에 저장한다. 이후부터는 인터프리터를 거치지 않고 코드 캐시에 저장된 기계어를 CPU가 직접 실행한다. 이처럼 프로그램 실행 중에 바이트코드를 기계어로 바꾸는 과정을 동적 컴파일이라고 이해하였다.

## 4. 1주차 웹 서버 과제 회고

1주차 과제에서는 Java 기반 웹 서버를 개선하였다. 기존에는 요청이 들어올 때마다 새로운 `Thread`를 생성하는 구조였지만, 이를 `ExecutorService` 기반의 Thread Pool 구조로 변경하였다. 이를 통해 매 요청마다 스레드를 새로 생성하는 비용을 줄이고, Worker Thread를 재사용할 수 있도록 개선하였다.

또한 `RequestHandler`에서는 HTTP Request를 읽고 Request Line과 Header를 파싱하도록 구현하였다. 요청 경로를 추출한 뒤 `resources/static` 디렉터리의 정적 HTML 파일을 읽고, HTTP Response Header와 Body를 생성하여 클라이언트에 응답하도록 만들었다.

이 과정에서 웹 서버의 동시성 처리 방식에 대해 고민하였다. 현재 구현은 Blocking I/O 기반이며, 요청 하나당 하나의 Worker Thread가 처리하는 구조이다. 또한 HTTP 요청 하나를 처리한 뒤 TCP 연결을 종료하기 때문에 Keep-Alive를 지원하지 않고, 요청마다 TCP 연결을 새로 생성해야 하는 비효율이 존재한다는 점도 확인하였다.

이를 계기로 웹 서버 구조를 더 확장해서 학습하였다. Blocking I/O와 Platform Thread Pool, Blocking I/O와 Virtual Thread, NIO와 Platform Thread Pool, NIO와 Virtual Thread 방식의 차이를 조사하였다. 특히 Tomcat과 같은 현대적인 웹 서버는 Keep-Alive를 지원하여 하나의 TCP 연결에서 여러 요청을 처리하고, NIO Poller가 연결을 감시하다가 요청이 도착했을 때만 Worker Thread를 할당하는 구조를 사용한다는 점을 알게 되었다.

이번 과제에서는 범위를 고려하여 Blocking I/O와 Platform Thread Pool 구조까지만 적용하였다. 하지만 HTTP 요청이 커널의 네트워크 스택을 거쳐 소켓의 InputStream으로 전달되고, 이를 애플리케이션 레벨에서 HTTP 프로토콜 형식에 맞게 파싱한 뒤 Response를 생성하는 전체 흐름을 이해할 수 있었다. 이후 단계에서는 Keep-Alive, MIME Type 처리, NIO 기반 구조까지 확장해서 학습하고 구현해 보고자 한다.
